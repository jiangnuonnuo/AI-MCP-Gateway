# 领域设计模式规范

本文档是项目架构索引的专项补充，遵循 [$xfg-ddd-skills](/Users/jiang/.codex/skills/xfg-ddd-skills/SKILL.md) 中的 Domain、Case 和 Infrastructure 设计准则。设计模式用于表达真实业务结构，简单流程保持直接实现，禁止为了套用模式而增加无意义的抽象。

## 选择原则

| 业务结构 | 采用方式 | 判断重点 |
| --- | --- | --- |
| 单一实现、步骤固定、规则简单 | 普通领域服务 | 没有可独立变化的实现或流程节点 |
| 同一接口存在多种实现，需要按类型或条件选择 | 策略模式 | 变化的是“怎么做” |
| 多个规则按固定顺序依次执行 | 规则链/责任链 | 变化的是“先后处理步骤” |
| 规则执行过程中存在条件分支、路由或不同终点 | 规则树 | 变化的是“走哪条路径” |
| 既有多种实现，又要经过多个校验和分支 | 组合使用 | 由 Case 或领域服务编排边界，分别保持模式职责 |

串联规则使用规则链，条件分支使用规则树，多实现选择使用策略。不要用大量 `if-else` 隐藏三类结构，也不要把三种模式混成一个无法测试的超大服务。

## 普通领域服务

适用于单领域内的简单查询、状态变更或固定步骤流程。服务可以直接依赖 Domain 定义的 Repository/Port，完成校验、执行和持久化。

当流程出现可独立变化的处理方式、多个可复用规则节点或明显的条件路由时，再拆出策略、规则链或规则树。小型领域模型可以直接由 Trigger 调用，不因形式上的分层而强制增加 Case。

## 策略模式

### 适用条件

- 同一业务动作存在两种或更多实现。
- 实现由类型、协议、状态或配置动态选择。
- 新增一种实现应尽量只增加策略类，不修改稳定的主流程。

### 结构约束

```text
Domain Service
    └── I{Xxx}Strategy
          ├── {First}Strategy
          └── {Second}Strategy
```

- 定义稳定的策略接口，接口参数使用领域实体、命令实体和值对象。
- 每个策略只负责一种变化方式；共享流程放入抽象基类或独立的领域能力中。
- 优先使用 `Map<业务类型, I{Xxx}Strategy>` 或技能中已有的 Factory 完成路由，避免在主服务中堆叠类型判断。
- 缺少策略、类型不支持和策略执行失败必须有明确的领域错误语义并记录必要日志。
- 策略需要访问外部系统时，只依赖 Domain 的 Port，不直接依赖 HTTP、DAO、Redis 等实现。

策略解决“选择一种实现”，不负责把多个步骤串起来。需要顺序处理时，应把每个步骤拆为规则节点或责任链节点。

## 规则链与责任链

### 适用条件

- 存在多个职责独立的校验、过滤或处理步骤。
- 步骤具有明确顺序，前一个节点的结果可以影响后一个节点。
- 节点需要复用、替换、调整顺序，或需要单独测试。

### 结构约束

```text
Root/Service → Rule-1 → Rule-2 → Rule-3 → Result
```

- 每个节点只完成一个业务规则，并通过 `DynamicContext` 或领域上下文传递中间结果。
- 由 Factory 或项目已引入的 `xfg-wrench-starter-design-framework` 组件统一组装链路。
- 链路顺序必须显式、可读且可测试；不能依赖不可见的 Bean 扫描顺序。
- 明确定义节点结果语义：继续、正常终止、业务拒绝和异常失败不能混用。
- 节点负责领域判断和上下文更新；数据访问仍通过 Repository/Port 完成。
- 日志记录规则名称、关键业务标识和结果，不输出密码、Token、API Key、Authorization 等敏感信息。

责任链解决“按顺序处理多个职责”，不适合表达大量条件分支。节点之间出现多条路径或不同终点时，应转为规则树。

## 规则树

### 适用条件

- 流程根据状态、类型、配置或业务结果动态选择下一步。
- 分支具有明确的业务含义，且路径会持续扩展或需要单独维护。
- 直接在服务中嵌套 `if-else` 会掩盖流程结构或造成职责混杂。

### 结构约束

```text
RootNode
   ├── BusinessNode-A ──> EndNode
   └── BusinessNode-B ──> BusinessNode-C ──> EndNode
```

- 使用 `RootNode` 作为入口，业务节点负责判断或执行一个明确步骤，`EndNode` 负责统一收敛结果。
- 由 Factory 创建并装配节点，节点路由规则应集中表达，避免分散在多个服务中。
- 使用 `DynamicContext` 承载本次流程的领域上下文，不使用静态变量保存请求状态。
- 使用项目已有的 `StrategyHandler`、节点基类和设计框架能力；先阅读对应 API 和现有实现，再新增节点。
- 每个分支必须定义命中条件、未命中路径、终止结果和异常语义，避免出现无路由或隐式默认分支。
- 规则树只负责流程路由，具体的多实现执行仍交给策略，连续校验仍交给责任链。

## 模式组合

复杂用例可以按职责组合：

```text
Case
  └── Domain Service
        ├── 责任链：前置校验与数据准备
        ├── 规则树：按业务条件路由
        └── 策略：执行选中的具体实现
```

组合时保持以下边界：

- Case 组织跨领域用例，不承载具体领域规则。
- 责任链只负责有序节点，规则树只负责条件路径，策略只负责一种实现。
- Domain 只使用 Repository/Port 抽象；Infrastructure 只实现适配和技术访问。
- 能用一个简单领域服务表达的流程，不引入完整的模式组合。
